## 2. 센서 데이터 정제 (`ingest.py`)

협력사 CSV를 **원본 그대로** `pressure`·`moisture` 테이블에 넣고, 그래프와 예측에 쓸 값은 정제해서 `sensor_10min`에 따로 둡니다. 원본을 고치지 않으므로 규칙을 바꾸면 다시 집계하면 됩니다.

### 2.1 정제 규칙

| 항목 | 규칙 | 이유 |
|---|---|---|
| 종류 구분 | `press` 컬럼이 있으면 측압, `uf`만 있으면 수분 | 두 CSV의 컬럼이 다름 |
| 내부온도 `temp_in` | `temp1~3` 평균, −100 이하 값은 뺌 | 센서 미연결이면 −127이 찍힘 |
| 측압 `weight_kg` | 절댓값 60 kg 초과는 뺌 | 협력사 기준 센서 오류값 |
| g 단위 센서 | 센서·날짜별 자동 판단: 그날 값의 20% 이상이 60~60000이면 ÷1000 (`GRAM_SENSORS`에 적힌 MAC은 항상 ÷1000) | 펌웨어에 따라 kg → g로 바뀜 (2026-10 중순 9288·A3E0, CDB0·CDE0·640xxx는 처음부터 g) |
| 외기 | 온도·습도가 둘 다 0이면 뺌 | 수신 실패 |
| 수분 `c_mo` | `rawMo` = 4095면 뺌 | 수분센서 미연결 |
| 빈 값 | `\0` → 빈 값 | 협력사 CSV 표기 |

### 2.2 10분 중앙값

정제한 값을 센서별로 10분 칸에 모아 **중앙값**을 저장합니다. 평균은 튀는 값 하나에 끌려가지만 중앙값은 거의 흔들리지 않습니다.

```
10분 안의 측압: 12.1, 12.3, 12.2, 58.0(튐), 12.4
평균   = 21.4  ← 튄 값에 끌려감
중앙값 = 12.3  ← 그대로
```

### 2.3 같은 파일을 두 번 올려도 안전한 이유

행마다 내용으로 MD5 해시를 만들어 `row_hash`(UNIQUE)에 넣고 `INSERT IGNORE`로 저장합니다. 해시가 파일 이름과 무관하므로 기간이 겹치는 CSV를 올려도 새 행만 들어갑니다. 집계는 파일에 든 센서·기간만 다시 계산합니다 (7일씩 나눠서).

## 3. 타설 시각 자동 추정 (`pour_detect.py`)

타설일 측압 그래프에서 "콘크리트를 언제 붓기 시작했고 언제 끝냈는지"를 찾습니다. 강도 예측은 타설 시작부터 적산온도를 쌓기 때문에, 이 시각이 없으면 예측할 수 없습니다.

### 3.1 바탕이 되는 현장 패턴

- 콘크리트가 센서 높이까지 차면 측압이 **계단처럼** 오른다. 같은 순간 내부온도가 뛰거나 떨어지는 경우가 많다.
- 센서 높이가 다르면 차오르는 순서대로 **수십 분 간격**을 두고 오른다.
- 거푸집 설치·망치질은 **센서 하나에서만 짧게** 튀고 온도 변화가 없다.
- 센서가 재부팅되면 온도가 −127로 찍히고 측압 영점이 다시 잡힌다.

### 3.2 처리 순서

**0단계. 1분 값 만들기** (`_minutes`)
측압은 1분 중앙값, 온도는 1분 평균으로 만듭니다. 설정에 없어도 값의 20% 이상이 60~15000 사이인 센서는 g 단위로 보고 kg로 바꿉니다. 정상이던 온도가 −127로 바뀌는 순간을 재부팅으로 표시합니다.

**1단계. 센서별 상승 찾기**

목표는 측압 그래프에서 **"콘크리트가 센서에 닿은 정확한 분"** 을 찾는 것입니다.
그런데 두 가지 바람이 서로 부딪힙니다.

- 망치질처럼 **한 번 튀는 값에 속으면 안 된다** → 값을 다듬어서(평활) 봐야 한다
- 시작 시각은 **분 단위로 정확해야 한다** → 다듬은 값은 늦게 반응해서 시각이 밀린다

그래서 **두 번에 나눠** 찾습니다. ① 다듬은 값으로 "이 근처에서 올랐다"를 대충 찾고, ② 다듬지 않은 원래 값으로 정확한 분을 되짚습니다.

**미리 알아 둘 말: 중앙값과 이동중앙값**

- **중앙값**: 숫자를 크기순으로 줄 세웠을 때 한가운데 값입니다.
  [0.2, 0.3, 8.5, 0.2, 0.3] → 줄 세우면 [0.2, 0.2, **0.3**, 0.3, 8.5] → 중앙값 0.3.
  평균(1.9)은 튄 값 8.5에 끌려 올라가지만, 중앙값은 튄 값이 줄 끝으로 밀려나서 영향을 받지 않습니다.
- **이동중앙값 (5분)**: 1분마다 "**나를 포함한 최근 5분** 값의 중앙값"을 구해 그 분의 값으로 씁니다. 계산 구간이 1분씩 옆으로 이동해서 "이동"이 붙습니다.

**예시 데이터** (센서 하나의 1분 측압, kg)

빈 거푸집이라 0.2~0.3 kg이다가, 08:59에 망치질로 한 번 튀고, 09:02에 콘크리트가 닿아 오르기 시작합니다.

| 시각 | 1분 값 | 최근 5분 (계산 구간) | 5분 이동중앙값 | 무슨 일 |
|---|---|---|---|---|
| 08:44~08:58 | 0.2~0.3 | | 0.2~0.3 | 빈 거푸집 |
| 08:59 | **8.5** | 0.2, 0.3, 0.2, 0.3, **8.5** | **0.3** | 망치질. 튄 값이 사라짐 |
| 09:00 | 0.2 | 0.3, 0.2, 0.3, 8.5, 0.2 | 0.3 | |
| 09:01 | 0.3 | 0.2, 0.3, 8.5, 0.2, 0.3 | 0.3 | |
| 09:02 | **4.0** | 0.3, 8.5, 0.2, 0.3, 4.0 | **0.3** | **진짜 시작**. 이동중앙값은 아직 못 따라옴 |
| 09:03 | 9.0 | 8.5, 0.2, 0.3, 4.0, 9.0 | **4.0** | 이제 따라 오름 |
| 09:04 | 16.0 | 0.2, 0.3, 4.0, 9.0, 16.0 | 4.0 | |
| 09:05 | 22.0 | 0.3, 4.0, 9.0, 16.0, 22.0 | 9.0 | |

표에서 두 가지를 볼 수 있습니다.

- **좋은 점**: 08:59에 튄 8.5는 이동중앙값에서 완전히 사라집니다. 망치질에 속지 않습니다.
- **대가**: 진짜 시작은 09:02인데 이동중앙값은 09:03에야 오릅니다. 5개 중 과반(3개)이 높아져야 중앙값이 바뀌기 때문입니다. 이렇게 **1~2분 늦게** 반응합니다.

**① 대충 찾기: "평소보다 3 kg 넘게 올랐다"**

이동중앙값이 **평소 수준보다 3 kg 이상** 올라선 분을 찾습니다. 평소 수준은 **직전 30분 동안의 이동중앙값 중 가장 낮은 값**으로 잡습니다.

- 09:02: 0.3 − 평소 0.2 = 0.1 kg → 아직 아님
- 09:03: 4.0 − 평소 0.2 = **3.8 kg ≥ 3** → **"09:03 근처에서 올랐다"** 로 잡힘

하지만 진짜 시작은 09:02이므로 1분 늦습니다. 그래서 ②로 되짚습니다.

**② 정확히 짚기: 원래 값으로 거꾸로 되짚기**

이번에는 다듬지 않은 **1분 원래 값**을 씁니다.

1. **평소 수준을 다시 잽니다.** ①에서 잡은 09:03의 **10~20분 전**(08:43~08:53) 1분 값들의 중앙값 = **0.2 kg**.
   바로 직전이 아니라 10~20분 전을 보는 이유는, 바로 직전에는 이미 오르기 시작한 값이 섞여 평소 수준이 높게 잡힐 수 있기 때문입니다.
2. **기준선을 긋습니다.** 평소 수준 + 1 kg = **1.2 kg**.
3. **09:03부터 15분 전까지 살펴, 기준선을 넘은 뒤 한 번도 아래로 내려오지 않은 첫 분을 찾습니다.**
   - 08:59: 8.5로 넘었지만 09:00에 0.2로 다시 내려옴 → 탈락 (망치질)
   - 09:00, 09:01: 기준선 아래
   - **09:02**: 4.0으로 넘고 그 뒤로 계속 1.2 위 → **시작 = 09:02**

결과적으로 **망치질(08:59)에도 속지 않고, 1~2분 늦지도 않게** 09:02를 찾습니다.

| 단계 | 쓰는 값 | 잘하는 것 | 혼자 쓰면 생기는 문제 |
|---|---|---|---|
| ① 대충 찾기 | 5분 이동중앙값 | 튀는 값에 속지 않음 | 1~2분 늦음 |
| ② 정확히 짚기 | 1분 원래 값 | 정확한 분을 찾음 | 튀는 값에 속음 |

두 방법이 서로의 약점을 메웁니다. 코드: [pour_detect.py:112-135](backend/app/pour_detect.py#L112-L135)

다음 후보는 버립니다.
- 상승 뒤 10분 측압이 1.5 kg 미만 (오류값에서 0으로 돌아온 것)
- 재부팅 전후 10분 안의 변화

**2단계. 묶어서 점수 매기기**

상승들을 시간순으로 놓고, 첫 상승에서 **30분 안에 시작한 것끼리 한 묶음**으로 봅니다.

```
점수 = 상승 폭 합 × (센서 2개 이상 함께 오르면 2) × (내부온도가 5분 새 1.5℃ 이상 변하면 2)
```

망치질은 센서 하나에 온도 변화도 없어 점수가 낮고, 진짜 타설은 여러 센서와 온도가 같이 움직여 높습니다. **최고 점수 묶음의 첫 상승 = 타설 시작**. 측압 센서가 하나뿐인 회차는 "함께 오름"을 따지지 않습니다 (항상 2배).

**3단계. 타설 종료**

시작 후 6시간 안에서 **묶음에 든 센서들의 측압 합이 최고인 분**을 종료로 봅니다. 다 부은 순간 측압이 가장 높고, 그 뒤로는 굳으며 줄어들기 때문입니다. 중간에 재부팅이 있으면 그 직전까지만 봅니다.

### 3.3 검증과 한계

- 협력사 2026년 시험 타설 5회차에서 측압·온도로 본 시각과 **0~1분** 차이. 실제 작업일지 시각과는 아직 비교하지 못했습니다.
- **30분 묶음 밖의 센서는 종료 계산에서 빠집니다.** 센서 높이 차이로 40분 뒤에 오른 센서는 다른 묶음이 되어, 종료가 이르게 잡힐 수 있습니다.
- **측압이 평평하게 유지되면** 잡음 때문에 평평한 구간의 앞쪽이 최고점으로 뽑힐 수 있습니다.
- 추정값은 확인용입니다. 화면(타설 시점 확인 탭)에서 사람이 확정값을 넣으면 그 값이 우선합니다.

## 4. 강도 예측 (`maturity.py`)

콘크리트는 따뜻할수록 빨리 굳습니다. 그래서 "얼마나 오래, 얼마나 따뜻했나"를 숫자 하나(적산온도)로 만들고, 그 숫자를 강도로 바꿉니다. 화면의 강도 예측 탭 숫자는 모두 `predict()` 하나에서 나옵니다.

```
predict()
  ├ train()                 강도 곡선 학습 (예측 회차는 뺌)       4.3, 4.6
  ├ pour_temperature()      이 회차 내부온도 (제외 구간 반영)      4.1
  ├ forecast_temperature()  앞으로의 온도 가정                    4.5
  ├ maturity()              적산온도                              4.2
  ├ scale_factor()          공시체로 회차 보정                     4.4
  └ first_crossing()        기준 강도 도달 시각                    4.7
```

### 4.1 온도 준비

- 적산온도에는 `sensor_10min`의 **내부온도(`temp_in`)만** 씁니다. 외기온도(`temp_out`)는 앞으로의 온도를 가정할 때 '내부 − 외기' 차이를 재는 데만 씁니다 (4.5).
- 회차에 센서가 여러 개면 같은 10분 칸의 값을 **평균**합니다.
- **6시간(36칸) 이내 공백**은 앞뒤를 직선으로 이어 채우고, 더 긴 공백은 비워 둡니다. 모르는 값을 지어내지 않기 위해서입니다.
- 설정 탭의 **제외 구간**은 빈칸으로 만든 뒤 앞뒤를 직선으로 이어 채웁니다. 원본은 지우지 않습니다.

### 4.2 적산온도 (Nurse-Saul, 기준온도 0℃)

10분마다 **(온도 − 0℃) × (10분 ÷ 1일)** 을 더합니다. 단위는 ℃·일입니다.

```
10분은 하루의 1/144 → 10분마다 (온도 × 1/144)를 더한다

15℃로 하루  = 15 × 1/144 × 144칸 = 15 ℃·일
20℃로 하루  = 20 ℃·일
10℃로 이틀  = 20 ℃·일   ← 위와 같으므로 강도도 거의 같다고 본다
```

온도 그래프 아래 넓이라고 보면 됩니다. 0℃ 이하는 거의 굳지 않는다고 보고 0을 더합니다.

```python
((T - DATUM_TEMP).clip(lower=0).fillna(0) * STEP / timedelta(days=1)).cumsum()
```

### 4.3 강도 곡선 (쌍곡선형)

```
강도 S = Su × k(M − M0) / (1 + k(M − M0))     (M < M0 이면 0)

Su : 오래 지나면 다다르는 최대 강도 (MPa)
k  : 강도가 오르는 빠르기
M0 : 강도가 오르기 시작하는 적산온도 (℃·일)
```

처음엔 빠르게 오르다가 점점 완만해지며 Su에 가까워지는 모양입니다.

**학습 방법** (`train`, `fit_curve`)
- 학습 회차들의 **현장양생** 공시체마다 (시험 순간의 적산온도, 실제 강도)를 점 하나로 만듭니다. 한 번 시험에 공시체가 3개면 점도 3개입니다.
- 수중양생 공시체는 현장 온도와 무관하므로 쓰지 않습니다. 온도 기록이 끝난 뒤 시험한 공시체도 그때의 적산온도를 몰라서 뺍니다.
- 모든 점에 가장 잘 맞는 Su·k·M0를 `scipy.optimize.curve_fit`으로 찾습니다. 범위: Su 5~80 MPa, k ≥ 0, M0 0~최대 적산온도.
- 공시체가 있는 회차가 **2개 미만**이면 학습할 수 없어 `config.py`의 고정 곡선(`FIXED_CURVE`)을 씁니다.

2026년 시험 타설 곡선으로는 **5 MPa에 약 28 ℃·일, 14 MPa에 약 103 ℃·일**이 필요합니다. 내부온도 20℃가 유지되면 각각 약 1.4일, 5.1일입니다.

### 4.4 회차 보정 (`scale_factor`)

같은 적산온도라도 배합·날씨·양생 상태에 따라 회차마다 강도가 다릅니다. 이 회차의 현장양생 공시체 결과가 있으면 **곡선 전체에 배율 하나를 곱합니다.**

```
1일 공시체 6 MPa, 곡선이 말하는 강도 5 MPa → 배율 ≈ 1.2 → 이 회차는 곡선 × 1.2
```

- 공시체가 여러 개면 모든 점에 가장 잘 맞는 배율 하나를 최소제곱으로 고릅니다: `Σ(실측×곡선) / Σ(곡선²)`.
- 실측·곡선 둘 다 **2 MPa 미만**인 결과는 뺍니다. 값이 작으면 비율이 크게 흔들리기 때문입니다. 추운 날은 1일 공시체가 2 MPa에 못 미쳐 보정이 빠질 수 있습니다.
- 배율은 **0.6~1.6배**로 자릅니다. 이상한 시험값 하나에 휘둘리지 않도록입니다.
- 기준 시각(as_of)까지 나온 결과만 씁니다.

정확도에 가장 큰 영향을 주는 단계입니다 (4.9 참고). 공시체 결과는 나오는 대로 입력할수록 좋습니다.

### 4.5 앞으로의 온도 (`forecast_temperature`)

아직 오지 않은 시간은 **기상청 예보 기온에 "콘크리트 − 외기" 차이를 더해** 가정하고 타설 후 30일까지 이어 붙입니다.

```
내부온도(t) = 외기(t) + 차이(t)
  외기(t)  = 기상청 단기예보 (약 4일, 1시간 간격 → 10분 간격 직선 연결), 그 뒤는 평년 기온
  차이(t)  = 0.6 + (지금 차이 − 0.6) × e^(−h/24)      h = 기준 시각 후 시간
  지금 차이 = 직전 24시간 '센서 내부 − 센서 외기' 평균
```

- **차이를 줄여 가는 이유**: 타설 직후에는 시멘트가 굳으며 열을 내서 내부가 외기보다 3~6℃ 높고, 며칠 뒤에는 거의 같아집니다 (재령 3~7일 중앙값 0.6℃). 예전 방식(직전 24시간 반복)은 이 따뜻한 첫날을 계속 반복해 **해체 시각을 이르게** 예측했습니다.
- **평년 기온**: 가까운 ASOS 관측소의 지난 5년 같은 날·같은 시각 평균 (앞뒤 7일로 고르게 폄). 서버가 처음 켜질 때 한 번 받아 `climate_normal` 표에 둡니다. 없으면 예보 마지막 하루를 반복합니다.
- **지난 기준 시각도 그때의 예보로**: 받은 예보는 `weather_forecast` 표에 쌓아 두고, 기준 시각 이전에 나온 가장 최근 예보(12시간 이내)를 씁니다. 그래서 최초 예상(4.8)도 타설 24시간 시점에 알던 예보로 다시 계산됩니다. 센서 데이터가 몇 시간 늦게 들어와도 기준 시각 이전 발표분이 있도록, 1시간마다 최근 24시간 안의 빠진 발표분을 채워 받습니다. 예보 API는 최근 3일치 발표분만 주므로, 그보다 오래된 시점(예보 수집을 켜기 전 회차의 최초 예상)은 `scripts.backfill_obs_forecast`로 **ASOS 관측 기온을 예보 대신** 채울 수 있습니다. 이때 `model.forecast`는 '기상청 관측 기온(그때 예보 대신)'으로 나오며, 완벽한 예보를 가정하는 셈이라 실제보다 잘 맞아 보입니다. `--normal`을 붙이면 관측 대신 **평년 기온**으로 채워, 그때 몰랐던 실제 날씨를 쓰지 않습니다 ('평년 기온(그때 예보 대신)').
- **예보를 못 쓰면 예전 방식**: 설정이 없거나, 그 시각에 받아 둔 예보가 없거나(이 기능을 켜기 전의 회차), 외기 센서 값이 없으면 **직전 24시간 내부온도를 그대로 반복**합니다. 직전 기록이 6시간도 안 되면 지금까지의 평균 온도로 채웁니다.
- 설정: `webapp/.env`의 `KMA_SERVICE_KEY`, `FORECAST_NX`·`FORECAST_NY`(현장 격자), `CLIMATE_STATION`(관측소). 화면의 `model.forecast`에 어느 방법을 썼는지 나옵니다.

**검증 (2026년 6회차 백테스트)**: 같은 곡선·보정에 미래 구간만 바꿔, 실제 측정 내부온도를 넣었을 때의 해체 기준 도달 시각과 비교했습니다. 미래 외기에는 기상청 **관측** 기온(완벽한 예보 가정)을 넣었습니다.

| 미래 온도 가정 | 평균 오차 | 타설 24시간 기준(최초 예상) |
|---|---|---|
| 직전 24시간 반복 (예전) | 13.3시간 | 11.2시간 (9시간 이르게) |
| 예보 4일 + 마지막 하루 반복 | 8.0시간 | 13.4시간 |
| 예보 4일 + 작년 같은 날 기온 | 6.0시간 | 4.2시간 |
| **예보 4일 + 평년 기온 (채택)** | **2.1시간** | **2.5시간** |

실제 예보는 관측보다 틀리므로 오차가 이보다 조금 큽니다 (예보 오차를 흉내 낸 시험에서 2~3시간 더해짐). 현장 센서 외기와 가까운 관측소 기온은 일평균 1℃ 안팎으로 맞았습니다. 겨울 회차가 하나뿐이고 겨울에는 장기 차이가 0.6℃보다 클 수 있어, 추운 날 예측은 여전히 주의가 필요합니다.

### 4.6 90% 범위와 보수적 시각

**공정한 평가 규칙: 예측하는 회차는 학습에서 뺀다 (LOPO).**
`predict()`는 `train(exclude_id=그 회차)`를 부릅니다. 지난 회차를 다시 볼 때도 자기 공시체 답을 미리 보지 않고, 늘 처음 보는 회차처럼 예측합니다.

**오차 크기 σ 재기** (`train` 안에서)
학습 회차 중 하나를 빼고 나머지로 곡선을 그려, 뺀 회차를 얼마나 틀렸는지 봅니다. 회차마다 돌아가며 반복합니다.

- 오차는 **"몇 배 틀렸나"** 로 기록합니다: `log(실측 / 예측)`. 강도가 클수록 MPa 오차도 커지므로 비율로 보는 것이 자연스럽습니다.
- 예측 3 MPa 미만인 점은 뺍니다. 아주 약한 구간은 비율 오차가 과장됩니다.
- 두 가지를 따로 잽니다.
  - `sigma_uncal`: 보정 없이 곡선만 썼을 때
  - `sigma_cal`: 재령 1.6일 이하 공시체로 보정한 뒤, 그 뒤 공시체를 얼마나 맞혔나 (보통 더 작음)
- 이 회차에 보정할 공시체가 있으면 `sigma_cal`, 없으면 `sigma_uncal`을 씁니다. 고정 곡선이면 0.3.

**범위 만들기**

```
하한 = 강도 × e^(−1.645σ)      상한 = 강도 × e^(+1.645σ)

예) σ = 0.18 → 하한은 강도의 약 74%, 상한은 약 134%
```

1.645는 정규분포에서 가운데 90%를 담는 값입니다. **보수적 시각 = 하한 곡선이 기준에 닿는 시각**입니다. 이때쯤이면 실제 강도가 기준을 넘었을 가능성이 약 95%입니다 (아래쪽 5%만 남으므로).

### 4.7 기준 강도 도달 시각

- 기준: 회차의 **해체 기준**(`criteria.py`, 아래 표)과 회차에 입력한 **설계기준강도**. 부재를 정하지 않은 회차는 최소값인 벽체 5 MPa·슬래브 14 MPa를 둘 다 봅니다.

| 부재 | 조건 | 해체 기준 (KCS 14 20 12 표 2.1.1) |
|---|---|---|
| 벽·기둥 측면 | 보통 / 내구성 중요 | 5 MPa / 10 MPa |
| 슬래브 밑면 | 단층 구조 (구조 형식 미선택 포함) | max(14, 설계기준강도 × 2/3) |
| 슬래브 밑면 | 다층 구조 | max(14, 설계기준강도) |

  설계기준강도가 없는 슬래브는 14 MPa로 계산하고 경고를 띄웁니다. 책임기술자 지시·필러 동바리 구조계산 같은 예외는 설정 탭에서 **직접 입력**할 수 있지만, 위 최소값(5 / 10 / 14 MPa)보다 낮게는 못 넣고 사유가 필수입니다 (변경 기록에 남음).
- **예상** = 강도 곡선이, **보수적** = 하한 곡선이 처음 기준 이상이 되는 10분 칸 (`first_crossing`). **타설 후 28일 안**에서만 찾고, 못 넘으면 "28일 내 미도달".
- **실측 보간** (`observed_crossing`): 공시체는 정해진 날에만 시험하므로, 기준을 넘기 직전 시험과 넘은 시험 사이를 직선으로 이어 추정합니다. 첫 시험에서 이미 넘었으면 언제 넘었는지 몰라 비웁니다.

```
3일 차 3.8 MPa, 7일 차 9.0 MPa → 5 MPa는 3일 + 4일 × (5−3.8)/(9.0−3.8) ≈ 3.9일
```

### 4.8 기준 시각과 최초 예상

- **기준 시각 `as_of`**: "이 시각에 서서 예측한다". 그때까지의 온도·공시체만 쓰고 그 뒤는 4.5처럼 가정합니다. 화면의 기준 시각 슬라이더가 이 값을 바꿉니다. 이미 끝난 회차를 그냥 열면 28일 공시체까지 다 넣은 사후 결과가 보이므로, 당시 예측을 보려면 기준 시각을 그때로 옮겨야 합니다.
- **최초 예상 `baseline`**: 타설 후 24시간 시점에 했을 예측을 다시 계산해서, 지금 예측과 비교합니다 (화면의 회색 점선, "최초 예상보다 n시간 늦음").

### 4.9 정확도와 한계

협력사 2026년 시험 타설 5회차, 회차 단위 교차검증 (3일 이내 강도):

| 조건 | RMSE |
|---|---|
| 공시체 보정 전 | 1.6 MPa |
| 1일 공시체로 보정 후 | 0.7 MPa |

- 학습 회차가 **5개뿐이고 겨울 회차가 없습니다.** 10℃ 미만 예측은 검증되지 않았습니다.
- 더운 날 친 회차는 14 MPa 이상에서 강도가 곡선보다 덜 자라, **슬래브 해체 시각을 이르게** 예측했습니다.
- 센서는 구조물 내부 온도를 재는데, 공시체는 작아서 그보다 온도가 낮을 수 있습니다.
- 벽체 5 MPa는 10℃ 이상에서 1일 공시체 보정 후 대체로 ±5시간 안에 맞았습니다.
- 배합이 회차마다 다르면 예측이 흔들립니다. 배합 정보는 아직 모델에 없습니다.

> 예측은 해체 시험 일정을 잡는 참고용입니다. 해체 결정은 현장양생 공시체 강도 확인과 현장 책임자 승인으로 합니다.

## 5. AI 상담 (`agent.py`)

### 5.1 원칙: LLM은 계산하지 않는다

강도·시각·온도는 모두 우리 코드(4장)가 계산합니다. LLM은 질문을 이해해 알맞은 도구를 고르고, 결과를 사람 말로 설명하는 일만 합니다. 숫자를 지어내지 못하게 하려는 구조입니다.

### 5.2 에이전트 루프

```
① 질문 + 시스템 프롬프트 + 최근 대화 10개 + 도구 목록 → LLM
② LLM이 tool_calls로 "get_prediction(pour_id=10) 불러 줘"라고 답함
③ 우리 코드가 그 함수를 실행하고 결과 JSON을 대화에 붙여 다시 LLM에 보냄
④ 부를 도구가 없다고 하면 그 글이 최종 답. 최대 6번 반복
```

| 도구 | 하는 일 |
|---|---|
| `list_pours` | 회차 목록, 타설 후 경과일, 진행 중 여부(28일 이내) |
| `get_prediction` | 강도·해체 시각 (4장 `predict` 결과 요약) |
| `get_temperature_summary` | 지정 구간 내부온도 마지막·최저·최고·평균 |
| `search_guideline` | 해체 가이드라인 검색 (6장) |

시스템 프롬프트의 주요 규칙: 수치는 도구 결과만 말한다, 해체 시각은 예상과 보수적을 함께 말하고 보수적을 권한다, 규정 질문은 검색 결과만 근거로 쪽수를 붙인다, 도구를 부를 때는 글 없이 한 번에 부른다.

### 5.3 스트리밍

`POST /api/agent/ask/stream`은 LLM 답을 조각으로 받아 JSON Lines로 바로 넘깁니다.

| 이벤트 | 뜻 |
|---|---|
| `step` | 도구 하나를 실행함 |
| `delta` | 답변 글자 조각 |
| `reset` | 방금까지 보낸 글은 답이 아니었음 (LLM이 쓰다가 도구를 더 부름) |
| `done` | 끝. 최종 답 전체와 걸린 시간 |
| `error` | 실패 |

LLM 서버의 생성 시간이 대부분이라 전체 시간은 20~30초 그대로지만, 첫 글자가 4~7초 안에 보입니다. LLM 호출은 생각 모드를 꺼서(`enable_thinking: false`) 약 4배 빠르게 했습니다.

## 6. 해체 가이드라인 검색 (`guideline.py`)

AI 상담의 규정·절차 질문에 근거를 찾아 주는 검색입니다 (RAG의 검색 단계). 두 검색의 **순위**를 합칩니다.

| 검색 | 강한 것 | 방법 |
|---|---|---|
| BM25 키워드 (직접 구현) | '14 MPa', 'KCS' 같은 정확한 숫자·용어 | 단어 그대로 + 두 글자 조각(bigram)도 색인. '해체시기'와 '해체 시기'를 같이 찾기 위해 |
| 임베딩 의미 검색 | '탈형'↔'해체', '바닥'↔'슬래브'처럼 단어가 달라도 뜻이 비슷한 것 | qwen-embedding 벡터 유사도. 조각 벡터는 색인에 미리 저장 |

**순위 합치기 (RRF)**: 두 점수는 단위가 달라 그대로 더할 수 없으므로 순위로 합칩니다.

```
최종 점수 = Σ 가중치 / (60 + 순위)        키워드 가중치 0.5, 의미 1.0
```

키워드 가중치 0.5는 `scripts/eval_guideline_search.py`로 1위 적중률·MRR을 비교해 정했습니다. 1.0이면 키워드 잡음이 정답을 밀어냈습니다.

- 색인은 ① 원문 PDF 색인(`app/data/guideline_chunks.json`, 재배포 금지라 저장소 밖) → 없으면 ② 팀 요약본 색인(`knowledge/summary_index.json`)을 씁니다.
- 임베딩 서버가 꺼져 있거나 늦으면 BM25만으로 검색해서 상담은 멈추지 않습니다.

## 7. 강도 알림 (`alerts.ts`, 자동 발송은 `notify.py`)

화면(대시보드 종 아이콘)에서 계산하고, 메일 초안을 열어 사용자가 메일 앱에서 직접 보냅니다. 메일 내용의 숫자는 모두 예측 결과에서 코드가 채웁니다 (LLM 미사용).

**SMTP 자동 발송**: `.env`에 `SMTP_HOST` 등을 넣으면 서버(`notify.py`)가 `NOTIFY_INTERVAL_MIN`(기본 10분)마다 같은 규칙으로 알림을 찾아, 회차 설정의 '알림 받을 메일'로 바로 보냅니다.
- 대상: 받는 사람이 있고 타설 후 28일이 지나지 않은 회차 (켜자마자 지난 회차 알림이 몰려 나가지 않도록). 한 회차의 알림 여러 개는 한 통으로 묶습니다.
- 보낸 알림은 화면과 같은 보냄 기록(`pour.notice`, 자동 발송은 `auto`에 표시)과 변경 기록('알림 메일 자동 발송', 사용자 `system`)에 남습니다.
- 발송에 실패하면 기록하지 않고 다음 확인 때 다시 보냅니다. 마지막 오류는 알림 패널에 보입니다.
- 규칙(종류·조건·키·문구)은 `alerts.ts`와 `notify.py` 두 곳에 있습니다. 바꿀 때 함께 바꿉니다.

알림은 **한 가지**: 부재 해체 기준 강도에 도달하기 **하루 전**.

- 지금 시각이 해체 기준 도달 **예상** 시각의 24시간 전(`BEFORE_HOURS`) 이후이고, 아직 기준에 도달하지 않았을 때 알립니다. 예상 시각이 24시간 넘게 지난 회차는 알리지 않습니다.
- 기준: 회차의 해체 기준(`criteria.py`). 부재 미지정이면 벽체 5·슬래브 14 MPa 각각. 설계기준강도는 알리지 않습니다.
- 같은 기준은 한 번만 알립니다 (키 `dayBefore:slab16`). 해체 기준 값을 바꾸면 새 기준으로 다시 알립니다.
- 초안을 열거나 서버가 자동 발송하면 "보냄"으로 기록(`pour.notice`)되어 같은 알림이 다시 뜨지 않습니다.

## 8. 용어

| 용어 | 뜻 |
|---|---|
| 회차 | 타설 한 번. 센서, 타설 시각, 공시체 결과가 회차에 묶임 |
| 공시체 | 타설할 때 같은 콘크리트를 작은 원통에 따로 담아 둔 시험용 조각. 정해진 날 눌러 깨서 강도를 잼 |
| 현장양생 / 수중양생 | 현장에 두어 구조물과 비슷하게 굳힘 / 물속 표준 온도에서 굳힘. 예측에는 현장양생만 씀 |
| 재령 | 타설 후 지난 시간 (1일, 3일, 7일, 28일 …) |
| MPa | 강도 단위. 클수록 단단함 |
| 적산온도 | 온도 × 기간의 합 (℃·일). 4.2 |
| 중앙값 | 크기순으로 세웠을 때 가운데 값. 튀는 값에 덜 흔들림 |
| 이동중앙값 | 각 시점마다 "최근 n개 값의 중앙값". 튀는 값은 없애지만 진짜 변화에도 조금 늦게 반응 |
| RMSE | 오차를 제곱해 평균 낸 뒤 제곱근. "보통 이 정도 틀린다"는 크기 |
| LOPO | Leave-One-Pour-Out. 회차 하나씩 빼고 학습해 뺀 회차로 채점하는 검증 |
| σ (시그마) | 오차가 퍼진 정도. 여기서는 log(실측/예측)의 표준편차 |
| 90% 범위 | 실제 값이 들어갈 것으로 보는 구간. 하한이 보수적 시각의 기준 |
| RAG | 문서를 검색해 찾은 내용을 근거로 LLM이 답하게 하는 방식 |
| BM25 | 단어가 얼마나 자주, 얼마나 드물게 나오는지로 문서를 점수 매기는 키워드 검색 |
| 임베딩 | 글을 뜻이 담긴 숫자 벡터로 바꾼 것. 벡터가 가까우면 뜻이 비슷함 |
